The module is split into two cooperating layers:

- `backend/app/db/` — runtime ORM layer. `base.py` declares a single `DeclarativeBase`; `models.py` defines all table classes (`Tenant`, `TenantWecomConfig`, `AdminUser`, `AdminSession`, `KeyVersion`, `SyncState`, `ArchiveMessage`, `ArchiveMessageRecipient`, `MediaFile`, `MessageRevocation`, `Contact`) as SQLAlchemy declarative models with `__table_args__` holding unique constraints, foreign keys, and PostgreSQL-specific indexes (GIN, functional tsvector). `session.py` provides a singleton `Engine` built from `DATABASE_URL` plus a `get_db()` generator for dependency injection. `schema_check.py` centralizes Alembic HEAD-vs-database revision comparison used by both HTTP readiness endpoints and deploy-time verification scripts. `contacts.py` is a thin helper module exposing tenant-scoped upsert logic.
- `backend/alembic/` — migration tooling. `env.py` wires Alembic to the same `Base.metadata` so model metadata drives migration generation; it reads connection info from `DATABASE_URL` or falls back to `DB_HOST/DB_PORT/DB_NAME/DB_USER/DB_PASSWORD`. `script.py.mako` customizes generated migration templates. `versions/` contains 12 sequential migrations (0001–0012) that evolve the schema from the initial key_versions/sync_states/archive_messages tables through tenant scoping, media storage backend references, structured message content, revocation integrity, thumbnails, etc.

Dependency direction is one-way: alembic imports `app.db.base` and `app.db.models` to discover metadata; application code imports models but never imports alembic at runtime.

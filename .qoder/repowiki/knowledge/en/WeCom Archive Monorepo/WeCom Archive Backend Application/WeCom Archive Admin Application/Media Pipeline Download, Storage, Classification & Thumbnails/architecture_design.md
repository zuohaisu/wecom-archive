The module is organized around a clear separation of concerns with a single storage abstraction driving all downstream logic:

- `media_storage.py` defines the `MediaStorageProvider` ABC plus `LocalStorageProvider` and the factory functions (`get_media_storage_provider`, `build_tenant_media_key`, `resolve_image_file_state`, `resolve_downloadable_media_state`). It also centralizes signed-URL TTL/window configuration and tenant-scoped key sanitization. This is the foundational layer.
- `qiniu_storage.py` implements the cloud backend as a `MediaStorageProvider` subclass; it is lazily imported so local-mode deployments never load the `qiniu` SDK or require credentials.
- `media_download.py` is the unified download worker: candidate selection (`build_candidate_query`, `select_candidates`), nested-media handling for mixed/chatrecord messages (`iter_nested_media_refs`, `select_nested_media_candidates`), atomic `.part`-then-rename writes, and the `download_one` core that streams chunks from the WeCom SDK, validates bytes via `detect_media_signature_from_bytes`, and persists through the provider.
- `media_classification.py` is a pure, stateless classifier driven by `app.message_type_registry.MessageSupportStatus`; it maps msgtype + has_sdkfileid to `MediaClassification(media_type, media_status, unsupported_reason)` and provides `resolve_image_media_status` / `resolve_downloadable_media_status` to combine with per-row storage state.
- `media_thumbnails.py` is a pure Pillow-based thumbnail generator (`generate_thumbnail`) returning `ThumbnailResult`, configurable via env vars and guarded against decompression bombs.
- `thumbnail_pipeline.py` orchestrates thumbnail generation + persistence for a single `MediaFile` row, used both by the download worker after a successful image download and by a backfill script; it is idempotent and never raises.

Dependency direction is strictly one-way: `media_download` → `media_storage` → (`LocalStorageProvider`, `QiniuStorageProvider`); `thumbnail_pipeline` → `media_thumbnails` + `media_storage`; `media_classification` depends only on `message_type_registry` and `SUPPORTED_MIGRATION_MEDIA_TYPES`. There is no cross-import between `media_download` and `thumbnail_pipeline` — they are coordinated by external scripts.

## 1. Context

[deliverables/final-roadmap-2026-07-29.md](../../deliverables/final-roadmap-2026-07-29.md)
建立在一个未经检验的前提上：**同时交付开源自托管版和云上商业版**。围绕它已经产生了
AGPL-3.0 授权、CLA、CONTRIBUTING、CODE_OF_CONDUCT、对外 README，以及一整个
「R2 · 开源发布闭环」里程碑。

2026-08-07 的讨论从第一性原理重审了这个前提。三件事被确定下来，它们共同推翻了原前提。

### 1.1 开源产生价值的路径是有限的，每条都有可证伪的前提

- **A 获客漏斗**：开发者发现 → 自托管 → 转云
- **B 可审计的信任**：买家需要验证软件不偷数据
- **C 外部劳动力**：外部贡献者修 bug、写集成
- **D 生态/标准**
- **E 品牌/招聘**

说不出要哪一条，就不该发布——因为每条对应的「做对了」形态完全不同。

### 1.2 目标客群被确定为 <5 座席的小微企业主

这个客群的性质决定了：

- **他们永远不会自托管。**不是嫌贵（服务器一年几百块），是根本做不到——
  没有人能跑 `alembic upgrade head`、配 SSL 续期、在腾讯 C SDK 段错误时看懂堆栈
  （见 [RND-208 记录](../RND-208-decryptdata-sigsegv.md)）。自托管对他们的成本是无穷大，
  **不构成定价上限**。
- **他们不逛 GitHub、不搜技术方案、不读 README。**机制 A 对这个客群等于零。
- 会自托管的是有 IT 团队的中大型企业——那是坐席多、能付大钱的客户。

由此得到一个反向的经济学：**开源等于把产品免费送给付得起钱的人，收费对象却是付不起钱的人。**

### 1.3 唯一能自洽的开源变现路径需要「做实施」，而我们不做

开源版若面向中大型企业与服务商，变现只能靠 AGPL 商业授权 + 私有化实施/服务。
**Haisu 明确不做实施，目标是完全自动化的云服务。**变现路径因此断裂，
开源只剩成本（永久性的公开披露约束、issue 与安全报告的接待、必须永远维护自托管升级路径），
没有任何回报。

### 1.4 客户买的不是「合规存档」，是「防飞单」

小微企业主不受金融/证券类留痕监管，没人查他的合规。他真实的动机是：
**怕员工私下加客户微信、私下报价、离职把客户带走。**

关键推论：**价值来自威慑，而威慑由员工的相信产生，不由老板的使用产生。**
老板不需要天天读聊天记录（5 个人他也读不过来），员工知道「老板能看到」就已经生效。

这个定位有一个结构性优势和一个结构性弱点：

- **优势**：产品装上就不用管，老板不登录、不提需求、不打电话。小微 SaaS 通常死于支持成本，
  威慑型产品天然没有这个成本。
- **弱点**：**成功和白花钱长得一模一样。**一年下来什么都没发生，老板分不出是产品在起作用
  还是本来就没人想飞单。流失会集中爆发在第一个续费点。

另一个关键推论：**威慑信号本身是腾讯免费发的**（开启会话存档时员工侧有知情提示），
但**腾讯只给 API、不给任何界面**——没有我们的产品，老板拿不到数据、看不到任何东西，
那个威慑就是虚张声势，而虚张声势只能撑到有人试探为止。

> **一句话卖点：不是「让员工知道你能看」——那是腾讯免费给的。
> 是「让你真的看得见」，这样那句话才不是吓唬人。**

## 2. Decision

### D1 · 不开源。仓库保持私有，改为专有许可

仓库当前仍是 PRIVATE，未推送任何公开版本——本决策的代价为零。
AGPL-3.0 的代码一旦公开发布即不可撤回，此刻是最后一个可逆时点。

### D2 · 只做一个产品：全自动化的云服务，面向 <5 座席小微企业

不做开源自托管版，不做私有化部署，不做实施服务。

### D3 · 产品定位是「防飞单威慑」，不是「合规存档」

1.0 的功能最低集 = **老板必须至少能搜一次、能看到一次**。不需要好用，但必须能用。

按此标准，[路线图](../../deliverables/final-roadmap-2026-07-29.md) 中已上线的 8 个页面
（登录 / 找回密码 / 重置密码 / 对话审阅 / 消息列表 / 消息详情 / 搜索 / 可达性诊断）
**恰好就是这个最小集合。1.0 的功能已经做完了。**

### D4 · 分发渠道走企业微信服务市场，为此申请成为第三方服务商

小微老板不在 GitHub，也不搜技术方案，但**他在企业微信管理后台里，而后台里就有服务市场**。
这是这个客群唯一自然的发现入口，且腾讯已替我们把客户筛选好——能看到该市场的人全都是企微企业主。

服务商资质与应用上架审核周期长，属于行政等待、不占开发时间，**应立即启动排队**。
需要接受的代价：审核可能特别严（读取全部对话）、可能的抽成、
以及从此有一个能随时改规则或下架我们的房东。

### D5 · 前 10 个客户刻意手工陪跑，不做自助 onboarding

「完全自动化」是 10 个客户**之后**的目标，不是之前的。

10 个客户不是收入目标（几万块不改变任何事），是**学习目标**，用来回答四个问题：
客户能不能自己配完腾讯侧、他们会不会续费、支持成本是不是真的接近零、私钥托管有没有出事。

不先手工的具体理由：**我们现在不知道真实用户会卡在哪一步。**凭空设计 onboarding 向导
必然自动化错的东西——把简单步骤做得很漂亮，把真正卡人的那步漏掉。
手工陪跑 10 家的成本远低于建一套自助向导，且产出一份买不到的**真实卡点清单**，
那份清单才是自动化的设计输入。

### D6 · 年付，不月付

威慑价值随时间衰减（越久没出事越觉得没用）。年付把续费决策一年只逼问一次，且现金流前置。
月付会在第 3 个月开始掉人。

### D7 · 月报推送算进 1.0

一封「本月已归档 12,384 条对话，覆盖 5 名员工，存档正常运行 31 天」的邮件/企微推送。
它不是让老板「爽」的功能，是**对抗 §1.4 那个结构性弱点的续费保险**——
让付钱的人每个月被提醒一次这东西还活着。成本是几小时，不是一个 dashboard。

## 3. Consequences

### 3.1 前 10 个客户真正必须做的工程只剩一件半

| 工作 | 前 10 家 | 理由 |
|---|---|---|
| **密钥体系租户化 + `app_secret` 加密落库** | ✅ 必须 | 10 家 = 10 把私钥，绕不过去 |
| **同步 worker 按租户调度 + 进程隔离** | ✅ 必须 | 一家段错误不能拖垮其他家 |
| 月报推送 | 🟡 便宜就做 | 续费保险（D7） |
| 服务商资质 + 应用上架 | 🟡 并行启动 | 行政等待，不占开发（D4） |
| onboarding 自助向导 | ❌ 推迟 | 手工陪跑，同时收集卡点（D5） |
| 注册 / 自助付费 / 发票 | ❌ 推迟 | 10 家可微信转账 + 手工开票 |
| dashboard / analytics / 告警 / 敏感词 | ❌ 2.0 | 锦上添花 |
| docker-compose / 自托管路径 | ❌ 降级 | 对客户无用；仅对自有部署环境仍有价值 |

原路线图的 R3（dashboard / analytics / 高级搜索）整波推迟到 2.0。
R1 四页快赢中，`users` 因需要邀请员工大概仍要保留，`audit-log` / `media` / `contacts` 可推迟。

### 3.2 全自动托管必然持有每一家客户的存档私钥

解密必须在服务端，无法绕开。这意味着我们握有 N 家公司全部员工与客户对话的解密能力。

小微客户不会 care（不懂也不问），**这正是危险所在——没有客户会替我们把关，只能自己把关。**
一次泄漏不是事故，是公司结束。

原路线图把它列为「阻塞 1（最严重）」是对的，但在「全自动 + 小微」组合下性质变了：
**从技术阻塞升级为这家公司唯一的存亡风险。**最低要求：信封加密、每租户独立密钥、
私钥绝不进日志/备份/DB 明文，且这套设计本身要能写进销售页。

### 3.3 腾讯的 C SDK 在多租户下必须做进程隔离

单租户时段错误只影响自己；多租户共进程时，一个客户的坏数据能把所有客户的同步搞停。
每租户独立进程/沙箱 + 失败隔离，是全自动云版特有的约束。

### 3.4 漏斗顶端有一道别人收的费

客户要体验产品，得先向腾讯付钱开通会话存档。在他掏钱之前，他一条数据都没有。
这对自助转化是毁灭性的。

**这一条已经做掉了**：`static_site/company_homepage/demo/` 下已上线一套纯静态、只读、
虚构数据的产品 Demo（会话审阅 / 搜索 / 联系人 / 媒体 / 统计），且官网主 CTA 就是「查看 Demo」。
它正是绕开腾讯付费闸门、让潜在客户在掏钱前看到产品的那件事。

后续若需要更真实的演示环境，仓库内还有
[`backend/scripts/mock_ingest.py`](../../backend/scripts/mock_ingest.py) 与
[`backend/scripts/seed_dev_analytics.py`](../../backend/scripts/seed_dev_analytics.py)
可以造带真实交互的样例租户。

### 3.5 对外官网已经上线，且已有真实访问

`static_site/company_homepage/` 是一套已部署的营销官网 + 静态 Demo
（由 [`scripts/deploy_server.sh`](../../scripts/deploy_server.sh) 随 main 分支自动发布到 nginx）。
2026-08-07 已有外部访问记录。

**本决策产生的对外不一致已于同日修复**：官网导航与页脚原有两处「开源项目」链接指向
**private 仓库**（点击即 404），FAQ 中另有一条承诺「开源项目可用于自行部署和评估」。
三处均已改掉——导航位改为「查看 Demo」，FAQ 改为说明本产品以托管服务提供、不提供自部署版本。

> **今后任何战略调整都要连带检查 `static_site/`。**它是唯一一处「改了仓库不改它就会对外说谎」的地方，
> 而且 merge 到 main 即自动上线。

### 3.6 需要清理的开源产物

见本次提交：LICENSE 换专有许可、删除 CLA / CODE_OF_CONDUCT、
CONTRIBUTING 转为内部 [docs/DEVELOPMENT.md](../DEVELOPMENT.md)、SECURITY 改为云服务口径、
README 去开源叙事。

## 4. Alternatives Considered

| 方案 | 否决理由 |
|---|---|
| **开源 + 云 SaaS（原路线图）** | 云的目标客群（小微）永远不会自托管，开源不给它带来一个客户；而会自托管的中大型企业是本可付大钱的一群。经济学是反的 |
| **开源 + AGPL 商业授权 + 实施服务** | 这是唯一自洽的开源变现路径，但需要做实施。已明确不做 |
| **Open-core（多租户/计费闭源，数据路径开源）** | 若认真承诺可审计（机制 B），几乎一切有价值的代码都触碰数据路径，能留在闭源侧的只剩计费与运营——最容易被重写的部分。撑不起商业模式 |
| **Source-available / 向客户单独开放源码审计** | 可逆、能拿到机制 B 的大部分收益。**未否决，保留为未来选项**——小微客户不要求审计，但若日后上攻中型客户可重新启用 |
| **先做完整自助 onboarding 再接客户** | 在不知道真实卡点前设计向导，必然自动化错的东西。见 D5 |

### 一处需要记录的判断修正

讨论前期曾断言「机制 A（开源获客）对中国 B 端接近于零」。**该断言是错的，已撤回**——
它套用了一个过窄的 A 定义（开发者逛 GitHub），并有明确反例：
飞致云（JumpServer / MeterSphere / 1Panel / DataEase）整家公司即建立在开源分发之上，
JumpServer 尤其结构相似（合规审计品类、自托管、IT 侧决策）；若依（RuoYi）则是服务商渠道的教科书案例。

**真正削弱 A 的是天花板而非转化率**：潜在用户被腾讯的会话存档付费闸门预先筛过，
是一个有限集合，而非无上限市场。最终否决 A 的理由是 §1.2 与 §1.3（客群不自托管 + 不做实施），
不是「开源在中国没用」。

## 5. Open Questions

### 🔴 OQ-1（阻断性）：会话存档是否支持第三方服务商 / 代开发模式？密钥那一步能否代劳？

D4 与转化率天花板整体压在这个问题上，**尚未查证，不得凭印象推进**。

已知的设计约束：会话存档的私钥由企业自己生成、自己保管，腾讯只收公钥——
**腾讯自身不持有解密能力**，这是它的隐私设计前提。若该设计是硬的，
「服务商代客户生成密钥」很可能恰恰是腾讯刻意不允许的那一步。

两种答案通向完全不同的产品：

- **能代劳** → 转化率天花板整体抬升，服务商路线成立
- **不能代劳** → 服务商模式只能简化 corpid / secret / 授权几步，**最难的密钥步骤照样得客户自己做**，天花板基本没动

**下一步**：查腾讯官方文档确认。这是整个计划里唯一「查一下就有答案、猜错则全盘皆错」的问题。

### 🟠 OQ-2：员工侧的知情提示，企微具体如何呈现？

一次性弹窗、持续可见标识、还是仅设置里可查？这决定威慑强度是「一次性、会淡忘」还是「持续在场」。

若是前者，1.0 可能还需要一个极轻的东西——**帮老板生成一份给员工签的告知书**。
那份纸贴在墙上的威慑力，可能比整个软件都大。

### ✅ OQ-3（已关闭）：定价已定并已对外公开

RND-239（2026-08-04 批准）已定价并**已上线官网**：

> **99 元/年，含 5GB 存储空间，不限座席**；超过 5GB 后每增加 1GB 加收 **1 元/GB/月**。
> 企业微信会话存档接口的开通及腾讯官方费用另计。

两个设计是对的：**超额计费直接挂在存储上**——唯一会随时间恶化的成本项与收入同向增长，
OQ-3 原本担心的问题在定价里已经解掉；**不限座席**则是相对腾讯按人头收费的正面差异点。

**但它把 §3 的一个约束顶到了极限**：99 元/年的基础档**无法吸收任何支持成本**。
一个客户在微信上问一次问题，这一单的毛利就没了。
「装上就不用管」不再只是定位优势，而是**唯一能让这个价格成立的前提**。
所有削减支持成本的投入（[W2 月报](../../deliverables/roadmap-first-10-customers-2026-08-07.md#w2--便宜但重要的两件小事)、
错误自愈、诊断页）应按此重新估值。

### ✅ OQ-4（已关闭）：命名由已发布的事实决定

RND-239（2026-08-04 批准）已确定并**已对外发布**：
中文 **康冠时代企业微信会话存档**，英文 **Crowntime WeCom Archive**，联系邮箱 `hs@crowntime.cn`。
Haisu 2026-08-07 确认闭源项目下仓库名 `wecom-archive-365` 暂不修改。

商标底稿中的「左正」不再是本产品的候选名，转为独立的商标储备。

**仍然存在的风险（未关闭）**：康冠时代商标第 17528858 号**有效期至 2026-11-13**
（见 `design/brand/BRAND.md`）。品牌名已经印在对外官网上，续展不能漏。

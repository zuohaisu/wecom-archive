# Ticket Autopilot 实战失败模式总结（2026-07-29 ~ 07-30）

> 用途：把「365 企微会话存档」项目移植 Ticket Autopilot 后、首个完整波次（R1，11 张票落地）中暴露的失败模式，整理成可回流 `AI-Operations` 上游的知识。
> 证据来源：本轮 **7 次 `BLOCKED_NEEDS_HUMAN`**、**1 次 QA FAIL（含错误 remedy）**、**1 次 CI hotfix 提交**（`fea4c94`），均有 git / Linear 实证。
> 标注 **[可移植]** 的条目适用于任何用 Autopilot 的项目；标注 **[本项目]** 的是实例知识，回流时应改写为「这一类」而非照抄。
> 流程沿革：本文保留 2026-07-29~30 的共享工作树历史证据；项目自 2026-08-14
> 起改用非 `main` worktree/分支与 PR merge。一票一个 commit；同 Epic 多票可在同一
> worktree 串行交付，并行票用不同 worktree，F7 的未提交改动混票风险由此消除。

---

## 0. 一句话结论

**本轮 7 次阻塞、1 次 QA 误判，没有一次是「代码难写」——全部是规格缺陷。**

在 AI agent 负责实现之后，瓶颈从「写代码多快」转移到了「规格多正确」。Autopilot 的投入产出比，因此几乎完全取决于**工单合同的质量**，而不是执行环节的智能程度。

推论：上游若要继续优化，**优化点在 ticket contract 与 ownership 的生成质量**，不在 executor。

## 2. 逐条：症状 / 根因 / 对策

### F1 — 所有权只列「被改的东西」，漏了调用方 **[可移植]**

**症状**：RND-326 要给模板加一个新变量 `__SIDENAV__`。所有权清单列了模板文件本身，但**模板不会调用自己**——真正需要同步传参的是两处调用点（生产路由 + 测试 shim）。不改它们，页面直接 500、大量既有测试在 collection 阶段就崩。开发 agent 正确停在 BLOCKED。

**根因**：拆所有权时按「内容在哪个文件」思考，而不是按「改完之后谁会坏」思考。

**对策（已落地）**：拆 ownership 前，对任何「新增/修改接口或变量」类工单，先用 grep 把**全部调用点**找出来再定清单。已写入 `docs/ticket-autopilot-workflow.md` §3.2。

**回流建议**：把这条作为 ticket-contract 生成阶段的强制自检项——*"列出本次改动的所有调用方/消费方，逐个判断是否需要随之更新"*。

---

### F2 — 漏了「守卫文件」的强制随附改动 **[可移植]**

**症状**：RND-288 新增一个路由。仓库里有两个守卫测试必然因此失败：
- `test_http_contract.py` 的 `assert route_count == 53`（硬编码基线）
- `test_rnd280_rbac_scaffold.py` 的**闭世界白名单**——其 `else` 分支断言「名单外的 router 不得出现 `require_role`」，因此**任何**新的 RBAC 路由都数学上必然失败

两者都不在所有权清单内 → agent 无路可走，QA 判 FAIL。

**根因**：同 F1 的变体，但更隐蔽——守卫文件不是「被改的东西的调用方」，而是「会被改动触发的断言」。

**对策（已落地）**：在 workflow doc 新增 §3.3，把「新增路由必须同步这两个文件」定为项目不变量，并写明**允许的最小改动范围**（只改计数 / 只加本票条目，不得动他票断言）。同时在今日 10 张票中**预先授权**。

**回流建议**：ticket-contract 增加一个判据——
> *把本工单的改动想象成已完成，然后问「验证闸会因此红在哪里」。红的地方全部属于本工单。*

这条比枚举具体文件更可移植。

---

### F3 — AC 规定了错误的机制 **[可移植]**

**症状**：RND-331 的 AC 写「`file_size` 收紧为 `NOT NULL`」。但该列有三态状态机（`pending`/`downloaded`/`failed`），`file_size` **只在下载成功时才存在**。盲目 NOT NULL 会打断正在跑的下载/重试流程。agent 只剩两个都错的选择：改超范围的文件，或填 `0` 撒谎。它正确地停下来了。

**根因**：AC 直接写了**实现机制**（NOT NULL），而不是**要保证的属性**（计费口径不能有空洞）。机制一旦写错，agent 无合法解。

**对策（已落地）**：改为条件性 CHECK 约束（`downloaded → file_size NOT NULL`），并把 AC 重写为**双向**要求：反例（downloaded+NULL 被拒）**且**正例（pending+NULL 仍可插入）。后者是防止"修好了计费、打断了下载"的关键。

**回流建议**：AC 应尽量写成**可观察的属性 + 反例**，而非实现指令。若必须指定机制，须同时给出「该机制不得破坏什么」的正例断言。

---

### F4 — 「后端 Done」≠「后端给得出前端要的东西」 **[可移植]**

**症状**：两次，性质递进——
- RND-329：列表 API 有数据，但**缺三个字段**（`msgid`/`conversation_id`/`session_title`），前端拼不出既有预览路由的 URL。
- RND-330：更糟——规划里指定的两个端点**根本不碰目标实体**（返回的是"归档参与者"和"内部员工"，而页面要的是"外部联系人"）。数据源整个是错的。

**根因**：路线图按 Linear 的 Done 状态推断可用性，没有实地核对**响应体形状与语义**。

**对策（已落地）**：拆出补齐票（RND-334 补字段、RND-288 补 API），并在页面票里写明「开工前先读实际响应确认字段名」。

**回流建议**：ticket-contract 里凡引用上游 API，必须记录**实测的响应字段清单**（而非"某某票已 Done"），并在 prompt 中要求 agent 开工前复核。**Linear 状态不是接口契约。**

---

### F5 — 依赖标签腐烂 **[可移植]**

**症状**：RND-311 连续 **3 次** BLOCKED。它的依赖标签是符号 `F0`，最初被假定指向"配置中心 epic"，后改判 RND-332，再因 RND-332 拆分改判 RND-333。每次 agent 都正确停下，但每次停的原因描述都指向一个**过期的票号**。

**根因**：符号化依赖标签（`F0`、`A7`）写下后从不被重新解析；而 epic 拆分 / 重排会让它悄悄指向错误对象。这类标签**不会报错**，只会误导。

**对策（已落地）**：把标签换成具体票号 + **可执行的验证命令**（`python -c "from app.crypto import encrypt_value"`），并在票里保留「沿革」说明为何变更，避免后人再推导一遍。

**回流建议**：依赖应记为 **(票号, 可执行的存在性检查)** 二元组，而非符号名。Autopilot 在派发前可自动跑一遍存在性检查，把「依赖未就绪」在派发前就拦下来，而不是浪费一次 agent 执行。

> 这条对上游价值最高：3 次 BLOCKED 本可被一条 `import` 检查全部避免。

---

### F6 — QA 验「调用了」而非「调用对了」 **[可移植]**

**症状**：RND-288 的 AC-4 要求 `owner_display_name` 复用既有 `resolve_person_display_name`。QA 用 grep 确认「函数被调用了」→ 判 PASS。但 QA 报告里引用的实际代码是：

```python
resolve_person_display_name(owner_wecom_userid, tenant_id)
```

而签名是 `(raw_id, name=None)`，函数体逻辑是「`name` 非空就直接返回 `name`」。传 `tenant_id` 会让**每一行的展示名都变成租户 UUID**——不报错、页面上看着有值、全是错的。

**根因**：AC 写成了「可 grep 的存在性」（复用了函数），而这类断言**天然无法覆盖参数正确性**。

**对策（已落地）**：AC 改为三段——① 调用存在 ② **逐字核对实参语义** ③ **行为断言**（有 Contact 时返回其 name；无则回退 raw_id；且 `!= tenant_id`）。

**回流建议**：凡"复用某函数"类 AC，必须配一条**行为断言**。grep 只能证明形式，不能证明正确。

---

### F7 — 共享工作树上的归因错误 **[可移植]**

**症状**：RND-288 的 QA 报告 `+3 routes`，把 `/admin/users` 与 `/admin/audit-logs` 也算在本票头上——那是另外两张票的在途未提交改动。本票实际只加 1 个路由。

**根因**：本项目并行方案是「直接在 main 上 + 文件所有权错峰」（不用 worktree），因此**多个 agent 的未提交改动共存于同一棵树**；而 `make verify` 跑的是整棵树，不是本票增量。

**对策（已落地）**：workflow doc 新增 §3.4，要求 QA **先 `git status --porcelain` 分离归因**，只把属于本票所有权清单的失败记在本票账上；无法分离时判 `BLOCKED`（需干净树复验），不得硬判 PASS/FAIL。

**回流建议**：这是「不用 worktree 换取合规」的**已知代价**，上游若采用共享树模式必须配套此纪律。反过来说——**这也是 worktree 隔离的核心价值论证**：上游原版用 worktree 就没有这个问题。

---

### F8 — QA 发明了违反不变量的 remedy **[可移植]**

**症状**：同一份 verdict 建议「把契约测试更新交给另一张维护票」。听起来合理，实则**会让 `main` 在两票之间持续红灯**，违反「main 始终可部署」。

**根因**：QA 被授权判定 PASS/FAIL，但没有被约束**不得发明流程方案**。它按"文件所有权"字面规则推理，得出了局部自洽、全局有害的结论。

**对策（已落地）**：在 QA 提示词里显式写明——契约同步是强制随附改动，**不得**建议拆票；此类情况 `recommended_next_state` 应为 `FIXING` 而非 `BLOCKED_NEEDS_HUMAN`。

**回流建议**：QA 的输出应限定在**判定 + 缺口描述**，流程性 remedy 需明确列为越权。或者：给 QA 一份「不可违反的不变量清单」（main 可部署、不拆强制随附改动…），让它的建议受约束。

---

### F9 — 脆弱守卫测试的长期税 **[可移植]**

**症状**：两个守卫测试反复制造摩擦——
- `assert route_count == 53`：硬编码魔数，**且与紧随其后的 expected path 集合断言功能重复**。路径集合已经能捕获路由增删，且失败信息更有用；计数只是多了一个会坏的地方，失败信息还什么都不说明。
- RBAC 闭世界白名单：把「谁被授权用 RBAC」这一**授权事实**放在测试文件里，而不是声明在 router 旁边。

今日 `fea4c94 hotfix for CI failure` 就是这个税的直接体现。

**根因**：守卫测试设计得脆弱，于是需要靠**文档提醒**来维持——而文档提醒是最弱的防御。

**对策（未落地，已提议）**：这是本轮唯一**没解决**的问题。真正的修法不是再写一段文档，而是改测试：
1. 删掉冗余的 `route_count` 断言（路径集合已覆盖，且失败信息更好）；
2. RBAC 白名单反转为**声明式标记**（router 自声明，测试读取），失败信息可变成「router X 用了 require_role 但未声明授权」。

**回流建议**：Autopilot 反复被同一类守卫绊倒时，**优先修守卫，而不是给每张票加提醒**。可作为一条元规则：*同一失败模式出现 ≥2 次 → 升级为工具修复，不再靠文档*。

---

### F10 — 提示词像文档，不像指令 **[可移植]**

**症状**：QA 提示词粘给 Qoder 后，它反问「你希望我做什么 / 这份提示词的目的是什么」，而不是直接开工。

**根因**：提示词通篇用描述性语气（"你是验收 agent"、"你可以…你不可以…"）——那是**规格语言**，不是命令。文中没有任何地方说明**何时开始**，也没有禁止先反问。对默认谨慎的 agent，这读起来就是"待审阅的参考材料"。

**对策（已落地）**：在模板与全部 17 份未使用的 QA 提示词顶部加「⚡ 立即执行，不要询问意图」块，明确：不要问意图、不要先出计划等确认、只读操作不需要许可、唯一合法的中止是把 `BLOCKED` **写进产出文件**（而不是向用户提问）。

**回流建议**：任何要粘给第三方 agent 的提示词，都应有显式的「立即执行」开场。不同 agent 产品的默认谨慎度差异很大，规格语气在保守的产品上会直接失效。

---

### F11 — 模板被实例知识污染 **[可移植]**

**症状**：我把「新增路由必须同步这两个具体文件」直接写进了 `dev-prompt-template.md`。用户指出：**模板不该承载特殊情况**。

**根因**：修 F2 时图省事，把项目事实写进了结构性产物。后果是每张未来的票都会带着两个可能与它无关的文件路径，模板从"形状"退化成"变更日志"，且与 workflow doc 两处重复、必然漂移。

**对策（已落地）**：模板只保留**通用判据**（"所有权清单 = 跑通验证闸所需的全部文件"）+ 指向 workflow doc，并注明不在此复制清单以免漂移。具体文件名留在 workflow doc（项目不变量）与各张票（实例）。

**回流建议**：三层分工要守住——
- **模板** = 结构（跨项目通用）
- **workflow doc** = 本项目不变量
- **ticket prompt** = 本工单实例

任何具体文件名出现在模板层，就是污染。

---

### F12 — 并行迁移抢 revision 号 **[可移植]**

**症状**：历史上 WorkBuddy 日志已记录 `287/297/306 抢 0020` 需人工定序。今日批次有 4 张票需要迁移，会重演。

**根因**：迁移号是**全局串行资源**，但工单是并行派发的。文件所有权错峰解决不了这个——它们的文件不冲突，冲突的是编号。

**对策（已落地）**：派发前**预分配序位**（当前 head `0023` → 332=`0024`、311=`0025`、316=`0026`、318=`0027`），写进每张票，并要求开工前复核 head 是否漂移。

**回流建议**：任何存在**全局串行资源**（迁移号、端口、固定文件名、序列号）的项目，编排器都应在派发阶段分配，而不是让并行 agent 自己抢。这是 worktree 隔离**也解决不了**的一类冲突——值得单独作为编排器职责。

## 4. 给 AI-Operations 上游的建议（按价值排序）

1. **依赖记为「票号 + 可执行存在性检查」，派发前自动跑一遍**（F5）。本轮 3 次 BLOCKED 可被一条 `import` 检查全部避免——这是投入产出比最高的一条。
2. **ticket-contract 增加「验证闸会红在哪里」自检**（F1+F2）。比枚举文件更通用，能一次覆盖两类所有权遗漏。
3. **AC 写属性 + 反例，而非机制**；「复用某函数」类 AC 必须配行为断言（F3+F6）。
4. **给 QA 一份不可违反的不变量清单**，约束它不发明流程 remedy（F8）。
5. **提示词加显式「立即执行」开场**（F10）——跨 agent 产品的鲁棒性问题。
6. **编排器负责分配全局串行资源**（迁移号等），worktree 隔离解决不了这类冲突（F12）。
7. **元规则：同一失败模式 ≥2 次 → 升级为工具修复，不再加文档**（F9）。
8. **共享工作树 vs worktree 的取舍要显式化**（F7）：不用 worktree 换来的是合规（不建分支），代价是 QA 必须自己做归因分离。上游原版用 worktree 就没这个问题——这条可作为两种模式的选型依据。
